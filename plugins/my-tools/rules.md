# 작업 규칙

답변은 한국어로 한다.

## 범위
- 요청한 것만 고친다. 관련해 옳아 보이는 수정도 말로 제안하고 승인을 기다린다. 두 변경이 한 세트인지는 사용자가 판단한다.
- 요청하지 않은 코드 주석은 넣지 않는다. 변경 이유는 답변에 쓴다.
- "안 보이게 해 달라"는 요청은 삭제하지 않고 주석 처리한다.
- "최소 구성"은 구현 범위를 줄이라는 뜻이지 설계에 있는 구성 요소를 빼라는 뜻이 아니다. 빼려면 먼저 묻는다.
- 인계서·절차서가 있으면 그대로 따르고 대안을 내지 않는다. 빠졌거나 현재 코드와 다른 점만 근거와 함께 짚는다.
- 구조가 확정되기 전에는 설계 문서·그림만 고치고, 실제 설정·스크립트 변경은 확정 후에 한다.

## 코드 스타일
- 쓰기 전에 주변 코드를 읽고 위치·이름·파일별 포맷·기존 패턴을 맞춘다.
- 기존 줄의 줄바꿈·들여쓰기를 바꾸지 않는다. 포매터를 돌리지 않는다.
- 쓴 직후 주변 코드와 다시 비교해 스스로 점검하고, 결과를 보고에 한 줄로 밝힌다.

## 커밋·푸시
- 사용자가 "커밋"이라고 말하기 전에는 커밋하지 않는다. 그 승인은 그 시점까지의 변경에만 한 번 유효하다.
- 항목마다 따로 커밋한다. 형식은 `feat:`/`fix:`/`refactor:` 등이고 내용은 한국어로 쓴다. 버그 수정은 `fix:`다.
- 스테이징은 파일명을 지정해서 한다(`git add -A` 금지). 사용자의 다른 미커밋 작업이 섞이지 않게 한다.
- push·force·amend는 따로 허락받거나 프로젝트에서 정한 경우에만 한다. 자기 브랜치에 push까지만 하고, 병합·MR 안내는 붙이지 않는다.

## 사실 확인
- 동작·규칙은 기억이나 추측으로 단정하지 않는다. 근거 파일·줄을 확인한 뒤 말하고, 확인 전이면 "확인해 보겠다"고 한다.
- 한 경우만 보고 일반화하지 않는다. 일부 구간만 확인했으면 확인한 구간을 나눠 말한다.
- "지금/아직/이미/남아 있다/없다" 같은 현재 상태는 그 답변 안에서 다시 조회한 뒤에만 말한다. 조회할 수 없으면 "확인하지 못했다"고 쓴다. 내가 제안한 명령은 사용자가 이미 실행했을 수 있다.
- 파일 위치·입수 방법을 물으면 먼저 실제로 찾아보고, 있으면 경로부터 답한다.
- 결함은 그 전제 조건을 실제 사용자가 화면에서 만들 수 있을 때만 "결함"이라 부른다. 확인된 결함 / 조건부 / 코드상 빈틈으로 나눈다. 내 주장이 반증되면 조건을 바꿔 되살리지 말고 먼저 인정한다.
- 전수 조사 결과에는 도구가 건너뛴 대상과 그 개수를 함께 적는다.
- 번역·문구 작업에서 원문에 없는 설명을 덧붙이지 않는다.

## 위험한 동작
- 서버 엔드포인트는 핸들러 코드를 읽기 전에 호출하지 않는다. GET도 작업을 실행할 수 있다.
- 시스템·서버 상태를 바꾸는 명령은 검증 목적이라도 먼저 묻는다. 사고가 나면 멈추고 영향을 조사해 그대로 보고한다.
- 운영 스크립트·서비스 파일 원본은 레포에 두고 시스템 위치에는 링크한다. 비밀값은 레포에 넣지 않는다.

## 설명
- 실행할 명령을 건넬 때는 지금 상황, 각 줄의 역할, 실행하면 벌어지는 일과 되돌릴 수 있는지를 쉬운 말로 함께 적는다. 전문 용어는 풀어 쓴다.
